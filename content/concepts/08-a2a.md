### 0. Яку проблему ми взагалі намагаємося вирішити?
Один agent може бути перевантажений усіма tools і доменами. Ми хочемо делегувати частину задач
іншому спеціалізованому agent і отримати результат/артефакт назад.
MCP добре описує agent ↔ tools/data, але для agent ↔ agent потрібна окрема модель взаємодії.
QA Agent needs code review
↓
Could directly own every tool...
або
↓
Delegate to Review Agent
### 1. Головна ідея простими словами
Ключова думка
A2A (Agent-to-Agent) — патерн/протокол взаємодії між агентами: discovery, capabilities, tasks, messages,
artifacts, status і handoff.
### 2. З яких компонентів це складається?
• Agent endpoint/card/capability description
• Task object
• Messages
• Artifacts
• Status lifecycle
• Authentication/authorization
### 3. Що фізично передається між компонентами?
Task request, context reference, message, artifact URI/content, status=working/completed/failed.
### 4. Що відбувається під капотом — крок за кроком

### 62. 2) Створює task із goal + constraints.
### 63. 3) Agent B приймає/відхиляє.
### 64. 4) Виконує власний harness/tool loop.
### 65. 5) Надсилає progress/messages/artifacts.
### 66. 6) Agent A отримує результат і включає його у свій workflow.

### 5. Де тут LLM, а де звичайний deterministic code?
LLM відповідає за probabilistic interpretation/decision/generation там, де потрібне розуміння природної
мови або вибір наступної дії. Усе, що стосується реального I/O, зберігання, permissions, network calls,
retries, schema validation, queues, databases і policy enforcement, виконується звичайним програмним
кодом та інфраструктурою. Межа між цими двома світами — одна з найважливіших mental models у
всьому курсі.
### 6. Повний простий приклад
QA Orchestrator передає Review Agent diff + standards. Review Agent повертає artifact review.json із issues.
Orchestrator вирішує, чи відправляти task назад Coding Agent.
### 7. Де це може впасти? — failure modes
• Agent unavailable
• Capability mismatch
• Handoff loses context
• Circular delegation
• Duplicate tasks
• Conflicting outputs
### 8. Security — що важливо захистити?
• Agent identity
• Scoped delegation
• Do not forward secrets blindly
• Artifact access control
• Audit delegation chain
### 9. Як це тестувати як QA/SDET?
• Discovery
• Task lifecycle
• Cancellation
• Timeout
• Partial artifacts
• Retry idempotency
• Cross-agent permission boundaries
### 10. Observability — що потрібно бачити в production?
traceId через усі agents, taskId, parentTaskId, delegation chain, latency, artifact lineage.
### 11. Production considerations
У production важливо думати не лише про happy path, а про versioning, backward compatibility, latency,
cost, retries, idempotency, rate limits, concurrency, degradation/fallback, data retention, deployment,
monitoring і incident response. Конкретна вага цих факторів залежить від цієї концепції, але production-
система завжди повинна мати контрольовану поведінку при часткових збоях.

### 12. Як ця концепція пов’язана з іншими?
Ця концепція не існує ізольовано. Попередній логічний крок: Concept 7 — Skills. Наступний: Concept 9 —
Multi-Agent System. Під час навчання завжди повертайся до глобальної карти: модель, harness,
state/memory, tools/MCP, RAG, A2A, guardrails, evals та observability — це шари однієї системи.
### 13. Коротка відповідь на співбесіді
**Interview answer**
A2A is about agent-to-agent delegation and collaboration—tasks, messages, artifacts and handoffs. MCP
typically connects an agent to tools/data; A2A connects one autonomous agent runtime to another.
### 14. “АААА, ось воно як!” — що треба запам’ятати
Не зубри визначення. Спробуй без документа намалювати flow від входу до виходу і для кожної стрілки
відповісти: хто це виконує, що саме передається, де зберігається state, де працює LLM, а де звичайний
код. Якщо можеш це відновити — концепція реально засвоєна.
